# Notion Page Contracts

Read this reference only after the proposed architecture has been approved.

## Workflow Page

- Purpose
- Use when
- Do not use when
- Required inputs
- Optional inputs
- Resources to load first
- Step-by-step process
- Decision points
- Output contract
- Quality checks
- Stop-and-ask conditions
- Completion criteria

A workflow page must describe an executable procedure rather than background knowledge.

## Reference Page

Begin with:

- What this reference contains
- When to consult it
- Which workflows depend on it
- Whether it is authoritative, advisory, or illustrative

Prefer a Notion page when the material is frequently consulted or behavior-critical. Retain an attachment when the source is asset-like, externally maintained, unusually long, or would lose important fidelity during conversion.

## Evaluation Page

- What is being evaluated
- Evaluation dimensions
- Observable pass/fail criteria
- Severity levels when relevant
- Scoring method when relevant
- Required remediation
- Conditions requiring revision
- Conditions for acceptance

## Example Page

Label each example as one of:

- Positive example
- Negative example
- Annotated example
- Style calibration
- Structural pattern

State what the example demonstrates. Never require the agent to infer the lesson solely from the sample.

## Notion Formatting

- Do not begin a page body with an H1 that duplicates the Notion page title.
- Use short sections, direct instructions, tables for routing, and callouts only for genuine warnings or non-negotiable rules.
- Keep page names stable and descriptive so routing links remain understandable.
- Avoid recreating filesystem folders when a database, tagged example library, or consolidated reference offers clearer navigation.
